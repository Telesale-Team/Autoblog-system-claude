## 1. เลือก V1 เป็นตัวจริง (เหตุผลเชิงโครงสร้าง)

**มติ: `booking_system.html` (V1) คือตัวจริง — ยกเนื้อดีจาก V2/V4 มาใส่**

เหตุผลเรียงตามน้ำหนัก ไม่ใช่ความชอบด้านหน้าตา:

1. **V1 เป็นเวอร์ชันเดียวที่เป็น "หน้าในเว็บ" ไม่ใช่ "ไฟล์ HTML ลอย"** — V3/V4 ไม่ extends `base_public.html` แปลว่าไม่มี navbar/footer จริง ไม่มี analytics ไม่มี font loader ไม่มี block SEO ที่เว็บใช้ร่วมกัน ถ้าเลือก V3/V4 ต้องรื้อกลับเข้า base ทั้งไฟล์ = เขียนใหม่ราว 60% ไม่ใช่ "แก้ต่อ"
2. **V1 ผูกกับ Design System จริง** (`--brand-navy` / `--brand-gold` จาก main.css) วันไหนแบรนด์เปลี่ยนสี หน้านี้เปลี่ยนตาม ส่วน V3/V4 hardcode ชุดสีของตัวเอง — V4 ถึงขั้นใช้เขียว emerald ซึ่งไม่ใช่สีแบรนด์ และใช้ชื่อแบรนด์ผิด ("จองดี") การเอาไปเสนอคือขายของคนละยี่ห้อกับเว็บที่ prospect เพิ่งอ่าน

## 2. แผนยุบ 4 → 1

**หลักการ: ต้องเหลือใบเดียวจริง ๆ ไม่ใช่ "เก็บไว้เผื่อ" เพราะเผื่อไว้แปลว่ายังต้องดูแล**

| ไฟล์ / URL | ทำอะไร | เหตุผล |
|---|---|---|
| `booking_system.html` · `/services/booking-system/` | **เก็บเป็นตัวจริง** | ตามมติข้อ 1 |
| `booking_system_v2.html` · `/services/booking-systemV2/` | **ลบไฟล์ + ลบ view + ลบ URL** หลังยกตารางเทียบและสาร 3 เสาเข้า V1 แล้ว | เนื้อดีที่สุดถูกดูดเข้า V1 หมด เหลือไว้ = ต้องแก้ราคา 2 ที่ทุกครั้ง |
| `booking_system_v3.html` · `...V3/` | **ลบทันที ไม่ต้องยกอะไร** | V4 คือ V3 เวอร์ชันใหม่กว่าและเนื้อเดียวกัน |
| `booking_system_v4.html` · `...V4/` | **ลบไฟล์** หลังยก pattern (sticky bar / ฟอร์ม 4 ช่อง / เลข section) เข้า V1 | ฟอร์มปลอม + แบรนด์ผิด + ราคาที่ถูก reject = ความเสี่ยงถ้าลูกค้าเผลอเปิดเจอ |

**URL เก่าจัดการยังไง:** ทั้ง 3 URL (V2/V3/V4) ไม่เคยถูกลิงก์จากที่ไหนในเว็บ และไม่มีใครแชร์ออกนอกทีม → **ลบ path ออกจาก `pages/urls.py` ได้เลย ไม่ต้องทำ redirect** ถ้าอยากปลอดภัยระดับที่สุด ใส่ `RedirectView.as_view(url='/services/booking-system/', permanent=True)` 3 บรรทัดแทนแล้วลบทิ้งในอีก 1 เดือน — แต่ลอยแนะนำลบตรง ๆ เพราะไม่มี traffic ให้ต้องรักษา

**ก่อนลบ:** ทุกอย่างอยู่ใน git แล้ว (V1 commit f5f4c70 / 2f20010, V2 4519a59) ถ้าวันหนึ่งอยากได้ตารางเทียบของ V2 คืน `git show` เอาได้ ไม่ต้องเก็บไฟล์เป็นสำเนาความปลอดภัย

**ต้องแก้ควบคู่:** `pages/views.py` ลบ 3 view · `pages/urls.py` ลบ 3 path · docstring ของ `booking_system()` เขียนใหม่ว่าเป็นหน้าเดียวที่มี

### 4.1 ฟอร์ม lead ไม่ต่อ backend (TODO บรรทัด 1187 / 1287)

**วิธีแก้เชิงดีไซน์ (เรียงตามที่ควรทำ):**

1. **ส่งเข้า `ContactLead` ที่มีอยู่แล้ว** — ไม่ต้องสร้าง model ใหม่ ใช้ `source="landing"`, `utm_*` ที่ `get_utm()` ใน views.py ดึงอยู่แล้ว, `company` = ชื่อร้าน, `message` = ประเภทร้าน + จำนวนสาขา, `consent_given` จาก checkbox PDPA (field รออยู่ครบ) — งานฝั่ง `ai-orchestrator` ไม่ใช่ของลอย ลอยส่งสเปกฟอร์มให้
2. **มีจุดสะดุด 1 จุดที่ต้องรู้ก่อน:** `ContactLead.email` เป็น required แต่ฟอร์มขายนี้ขอ LINE/เบอร์ ไม่ขออีเมล → ต้องแก้ให้ `blank=True` หรือกำหนดค่าแทน **นี่น่าจะเป็นเหตุผลจริงที่ TODO ค้างมา 55 วัน — ไม่ใช่เพราะยาก แต่เพราะไม่มีใครชี้จุดนี้**
3. **UI หลังกดส่ง:** ใช้ pattern thank-you inline ของ V4 (สลับกล่องฟอร์มเป็นข้อความยืนยัน + สรุปสิ่งที่ส่ง) แต่ต้องขึ้น **หลังได้ response สำเร็จจริงเท่านั้น** ห้ามขึ้นก่อนเด็ดขาด (บทเรียนจาก V4)
4. **LINE ยังอยู่ แต่เปลี่ยนบทบาท** — จาก "วิธีส่งฟอร์ม" เป็นปุ่มคู่ขนาน "อยากคุยเลย ทัก LINE" สำหรับคนใจร้อน ส่วนฟอร์มคือช่องทางที่เก็บข้อมูลได้
5. **ระหว่างที่ backend ยังไม่เสร็จ (ถ้าต้องเสนอลูกค้าสัปดาห์นี้):** เปลี่ยนคำบนปุ่มจาก "ส่งข้อมูล" เป็น **"เปิดแชท LINE พร้อมข้อความ"** และตัด "เราติดต่อกลับภายใน 1 วันทำการ" ออก — สัญญาเฉพาะสิ่งที่ระบบทำได้จริง

### 4.2 หน้ายาว 1,300+ บรรทัด — บนมือถือ prospect จะถึง CTA ไหม

**ประเมิน:** 1,312 บรรทัดคือ markup จริงราว 420 บรรทัด (ที่เหลือเป็น CSS ใน `extra_css` ราว 400 บรรทัด) ความยาวที่ prospect เจอคือ **ราว 11 หน้าจอมือถือ** ถ้าเข้าจากลิงก์ LINE ตอนพักเที่ยง โอกาสถึงฟอร์มท้ายหน้าต่ำมาก

**แก้ 5 ชั้น โดยไม่ต้องตัดเนื้อหาทิ้ง:**

1. **Sticky topbar ที่มี CTA** (ยกจาก V3/V4) — สูงราว 52px พื้นโปร่ง blur ปุ่ม "ทัก LINE" อยู่ตลอด → CTA เลิกผูกกับตำแหน่งท้ายหน้า **นี่คือการแก้ที่ได้ผลมากที่สุดต่อแรงที่ลง**
2. **CTA แทรกกลางทาง 2 จุด** — ท้าย section 05 (ของจริง) และท้าย section 09 (ราคา) เป็นแถบบาง ไม่ใช่บล็อกใหญ่ ให้คนที่ตัดสินใจแล้วออกได้เลยโดยไม่ต้องอ่านจนจบ
3. **ย่อ section บนมือถือ** — Pain / หลังบ้าน / FAQ แสดง 3 รายการแรก + "ดูทั้งหมด" ด้วย `<details>` ธรรมดา ไม่ต้องใช้ JS ลดความสูงมือถือได้ราว 30%
4. **เลข 01–09 บน section** (ยกจาก V4) — บอกความยาวที่เหลือ ลด bounce จากความรู้สึกว่าหน้าไม่จบ
5. **`--nd-pad: 6rem 0` ต้องลดเหลือ ~3.5rem บนมือถือ** — ตรวจแล้วว่าตัวแปร `--nd-pad-sm` ถูกประกาศไว้ตั้งแต่แรกแต่ **ไม่เคยถูกเรียกใช้ใน media query เลย** ระยะห่าง 6rem × 11 section คือความสูงที่เสียไปฟรี ๆ หลายจอ

### 4.3 ราคาบนการ์ด `/services/` (฿25,000) ไม่ตรงกับหน้าขาย (฿9,900)

**สาเหตุจริงลึกกว่าเรื่องราคา:** ในระบบมีสินค้าตัวเดียวกันอยู่ 2 ที่ ที่ไม่รู้จักกัน

- DB `Service`: `slug="booking-massage"` ชื่อ "เว็บไซต์ Booking ร้านนวด" ราคา 25,000 → เรนเดอร์ด้วย `service_detail.html`
- Template จริง: `/services/booking-system/` → หน้าขาย QueueFlow 9,900

การ์ดบน `/services/` ลิงก์ไปตัวแรก **หน้าขายที่ลงแรงทำจึงไม่มีทางเข้าถึงจากภายในเว็บเลย**

**แก้ (สเปกให้ `ai-orchestrator` ทำ — ลอยไม่แตะ view/model):**

1. **แก้ record ใน DB ให้เป็นตัวเดียวกัน:** slug `booking-massage` → `booking-system`, ชื่อ → "QueueFlow — ระบบจองคิวออนไลน์", `price_start` → 9,900, `price_label` → "ค่าติดตั้ง เริ่มต้น"
2. เพราะ `path("services/booking-system/")` ประกาศ **ก่อน** `<slug:slug>` ใน urls.py อยู่แล้ว → พอ slug ตรงกัน การ์ดจะพา prospect เข้าหน้าขายจริงทันที **ไม่ต้องแก้ template การ์ดแม้แต่บรรทัดเดียว**
3. เพิ่ม field `landing_url` (nullable) ใน `Service` เผื่อสินค้าตัวถัดไป — สินค้าไหนมีหน้าขายเฉพาะก็ใส่ URL ไว้ สินค้าไหนไม่มีก็ตกไป `service_detail.html` ตามเดิม **นี่คือกลไกที่ทำให้สินค้าตัวที่ 2 (POS) ไม่ต้องมาแก้ urls.py อีก**
4. **กฎถาวร:** ราคาต้องมีแหล่งความจริงเดียว — ให้หน้าขายดึง `{{ svc.price_start }}` จาก DB แทน hardcode `฿9,900` ในเทมเพลต จะได้ไม่หลุดกันอีก (tier 2/3 ยัง hardcode ได้ ถ้ายังไม่อยากทำ model ราคาแบบ tier)

## 5. สินค้าตัวที่ 2: ระบบสต๊อก + POS — ใช้โครงเดิมซ้ำได้ไหม

**ตรวจแล้ว: ในโปรเจกต์ยังไม่มีอะไรเลยสำหรับ POS** — ไม่มี template ไม่มี Service record ใน seed ไม่มีภาพปก

**คำตอบ: ใช้โครงเดิมได้ราว 85% แต่ต้องยกให้เป็น "แม่แบบ" ก่อน ไม่ใช่ copy ไฟล์**

เหตุผลเชิงโครงสร้าง: 11 section ข้างบนคือลำดับการตัดสินใจของเจ้าของกิจการ SME ซึ่งเหมือนกันไม่ว่าจะขายระบบจองหรือระบบสต๊อก — **สิ่งที่เปลี่ยนคือเนื้อ ไม่ใช่โครง** ถ้า copy ไฟล์ไปแก้ จะกลับสู่สภาพเดิมทันที (CSS ซ้ำหลายไฟล์ แก้สีต้องแก้ n ที่ ซึ่งคือสาเหตุที่วันนี้ต้องนั่งยุบ 4 ไฟล์)

### วิธีทำแม่แบบ (สเปกสำหรับรอบหน้า ยังไม่ต้องทำตอนนี้)

1. **ย้าย CSS ราว 400 บรรทัดใน `extra_css` ออกเป็น `static/css/salepage.css`** — คลาส `nd-*` ถูกออกแบบให้ generic อยู่แล้ว (`.nd-device`, `.nd-pkg`, `.nd-h2`, `.nd-btn`) เปลี่ยน prefix `qf-` → `sp-` (sale page) ให้เลิกผูกกับ QueueFlow **ทำให้หน้าขายใบที่ 2 เขียนแค่ markup ไม่ต้องเขียน CSS เลย**
   - หมายเหตุตาม anti-pattern ของลอย: ปกติห้ามใส่คลาสเฉพาะหน้าเดียวใน main.css — แต่เมื่อใช้ตั้งแต่ 2 หน้าขึ้นไปและแยกเป็น `salepage.css` ที่โหลดเฉพาะหน้าขาย ถือว่าผ่านเกณฑ์ reuse
2. **แตก 11 section เป็น partial** ที่ `pages/templates/pages/_sale/` (`_hero.html`, `_proof.html`, `_pain.html`, `_flow.html`, `_showcase.html`, `_pillars.html`, `_compare.html`, `_features.html`, `_pricing.html`, `_faq.html`, `_leadform.html`) — หน้าใหม่คือไฟล์ include 11 บรรทัด + context
3. **ฟอร์ม lead เป็น partial ตัวเดียวทั้งเว็บ** — POST ไป endpoint เดียว ส่งชื่อสินค้าไปด้วยเพื่อแยกใน `ContactLead.message` / `utm_campaign` แก้ครั้งเดียวได้ทุกสินค้า

### สิ่งที่ POS ต้องเปลี่ยนจริง ๆ (ไม่ใช่แค่เปลี่ยนคำ)

| จุด | ระบบจอง | ระบบสต๊อก + POS | ผลต่อดีไซน์ |
|---|---|---|---|
| คนตัดสินใจ | เจ้าของร้านบริการ | เจ้าของร้านค้า / คนคุมสต๊อก | เปลี่ยนคำ ไม่เปลี่ยนโครง |
| ความเจ็บ | ตอบแชทดึก คิวชน | **ของหาย ของขาด นับสต๊อกไม่ตรง ไม่รู้กำไรจริง** | section 03 เขียนใหม่ทั้งหมด |
| ของที่ต้องโชว์ | หน้าจองฝั่งลูกค้า | **หน้าขายหน้าร้าน + รายงานสต๊อก + ใบเสร็จ** | section 05 ต้องมี screenshot ใหม่ 3 ภาพ |
| section ที่ต้องเพิ่ม | – | **ฮาร์ดแวร์ที่ใช้ได้** (เครื่องอ่านบาร์โค้ด / ลิ้นชักเงิน / เครื่องพิมพ์สลิป) | เพิ่ม 1 partial `_hardware.html` ใช้ซ้ำได้กับสินค้า AI+Hardware ในอนาคต |
| ตารางเทียบ | Fresha / GoWabi | **ต้อง research ใหม่** (Loyverse / StoreHub / FlowAccount ฯลฯ) | ต้องสั่ง `market-research-analyst` ก่อนเขียน section 07 — ห้ามแต่งตัวเลข |

### สิ่งที่ POS ยังไม่มีและต้องสั่งงาน (ตามลำดับ)

1. `market-research-analyst` — คู่แข่ง POS ไทย + ราคา benchmark (ขาดอันนี้ section 07/09 เขียนไม่ได้)
2. `money-manager` — เคาะราคา 3 tier
3. **screenshot ระบบจริง 3–5 ภาพ** — ถ้ายังไม่มีระบบให้ถ่าย นี่คือคอขวดตัวจริง หน้าขายที่ไม่มีภาพของจริงคือ V3/V4 ซึ่งเราเพิ่งตัดสินใจว่าใช้ไม่ได้
4. `graphic-designer` — ภาพปก/OG + diagram flow (POS ยังไม่มีภาพปกแม้แต่ภาพเดียว)
5. ลอย — ประกอบจาก partial (ถ้าทำแม่แบบตามข้อ 1–3 แล้ว เหลืองานราวครึ่งวัน)

**คำเตือนเรื่องจังหวะ:** อย่าเพิ่งทำแม่แบบตอนนี้ ให้ **ยุบ 4→1 + ต่อฟอร์ม + แก้ราคา ให้จบก่อน แล้วค่อยแตก partial ตอนจะทำ POS** — แตก partial ตอนมีหน้าเดียวคือ over-engineering แตกตอนมีหน้าที่ 2 คือถูกจังหวะพอดี
